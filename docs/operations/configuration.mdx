## Runefile errors and typos

`runed` reads the runefile at startup and treats two mistakes differently:

- **A value of the wrong type** stops startup. For example, a scalar where the config expects a table:

  ```yaml
  secret:
    encryption: "on"   # expected a table (kek, ...)
  ```

  `runed` logs `Runefile does not decode`, names the file and the problem, and exits with status 1. A runefile that doesn't parse at all fails earlier, the same way (exit 1, `Failed to read runefile`).
- **A key it doesn't recognise**, usually a typo, does not stop startup. `runed` logs one ERROR listing every unknown key, and the setting you meant stays at its default. Search the log for `Runefile keys are not recognised`.

Unknown keys are tolerated on purpose: after a `rune upgrade` rollback, an older `runed` must still start on a runefile written for a newer one. A [few keys](/reference/runefile) are read outside the main config (such as `debug`, `pretty`, `docker.registries[].auth.from_secret`) and are not reported.

<Note title="Since v0.0.1-dev.148">

Since v0.0.1-dev.148. Before that, a wrong-typed value can crash `runed` and unknown keys are ignored silently.

</Note>

## Addresses and exposure

Default config binds to all interfaces:

```yaml
server:
  grpc_address: ":7863"
  http_address: ":7861"
```

For a single-host setup with no remote API consumers, lock to localhost and let the CLI tunnel via SSH:

```yaml
server:
  grpc_address: "127.0.0.1:7863"
  http_address: "127.0.0.1:7861"
```

Then:

```sh
ssh -L 7863:localhost:7863 host
rune login local --server localhost:7863 --token-file ./tok
```

Without TLS, every bearer token crosses the wire in plaintext, so don't expose the gRPC port to an untrusted network. `runed` can serve gRPC over TLS (`server.tls`, see the [runefile reference](/reference/runefile#server-tls)), but the `rune` CLI can't connect over it yet; until it can, keep the port on loopback and use the SSH tunnel above.

## Auth posture

```yaml
auth:
  allow_remote_admin: false
```

Authentication is always on: every request needs a bearer token, and there is no runefile switch to turn that off.

- `allow_remote_admin: true` removes the localhost gate on `admin/*` RPCs. Don't enable on a public network without TLS plus an aggressive firewall.

## Storage limits

```yaml
secret:
  limits:
    max_object_bytes: 1048576     # default 1 MiB
    max_key_name_length: 256      # default 256
config:
  limits:
    max_object_bytes: 1048576
    max_key_name_length: 256
```

These cap the size of a whole secret or configmap and the length of its key names — useful when handing tokens to less-trusted CI bots. Tune up only if you actually need bigger payloads (e.g., larger TLS certs). Limits are enforced when an object is created or updated; an existing object over a lowered limit stays readable and is rejected on its next write.

<Note title="Unreleased">

On `dev`; ships after v0.0.1-dev.148. Until then the snake_case keys above were ignored (the 1 MiB and 256 defaults always applied), and only the run-together `maxobjectbytes` / `maxkeynamelength` spellings took effect.

</Note>

## KEK source

```yaml
secret:
  encryption:
    kek:
      source: file              # file | env | generated
      file: /var/lib/rune/kek.b64
```

In order of operational preference:

1. **`source: env`**, reading the `RUNE_MASTER_KEY` environment variable (the name is fixed) — load from a secret manager (Vault, AWS Secrets Manager, systemd credential) at boot.
2. **`source: file`** — KEK on disk with mode `0600`. Easiest. Back it up.
3. **`source: generated`** — only for ephemeral test setups. Dies with the process.

Always back up the KEK separately from the database. Lose the KEK, lose all secrets — there's no recovery.

## Runners

`runed` starts both the Docker runner and the process runner when it can, and each service picks one with its `runtime`. There is no runefile switch to disable either. On a host without Docker, container services fail with a clear error and process services keep working. Docker tuning keys are under [`docker`](/reference/runefile#docker).

## Registries

Two ways to manage:

```yaml
# Static — in the runefile
docker:
  registries:
    - name: ghcr-private
      registry: ghcr.io
      auth:
        type: basic
        username: ${GHCR_USER}
        password: ${GHCR_PAT}
```

Or dynamic at runtime:

```sh
rune admin registry add --name ghcr-private \
  --registry ghcr.io --type basic \
  --username "$GHCR_USER" --password "$GHCR_PAT"
```

Runtime registries don't require a `runed` restart. Static ones do.

`registry` can carry a repository path (`ghcr.io/myorg`), not only a
host — the credential then claims only the repositories beneath it, and
everything else on the host pulls anonymously. When several entries
match one image the most specific one wins. See
[`docker.registries[]`](/reference/runefile#docker-registries) for the
precedence rules and the `type: none` public carve-out, and
[Pull from GHCR](/guides/ghcr-auth) for the end-to-end GitHub Container
Registry walkthrough.

## Logging

```yaml
log:
  level: info        # debug | info | warn | error
  format: json       # text | json
```

For production, use `json` and ship to your log collector. For local debugging, `text` is easier on the eyes.

## Common tuning recipes

### "I'm seeing slow `rune cast`."

Probably docker pull latency. Pre-pull images on the host or check registry network reachability. The server itself is rarely the bottleneck for single-node workloads.

### "Secrets feel risky."

- Move `secret.encryption.kek.source` from `file` to `env` and load via systemd `LoadCredential`.
- Tighten `secret.limits` so accidental large writes are caught.
- Restrict the `secret` resource in policies — only on-call gets `get` for `*` namespace.

### "I want minimal blast radius for the gRPC port."

- Bind to localhost.
- Run a reverse proxy (Caddy, nginx) with mTLS on a public port.
- Set `auth.allow_remote_admin: false` (default).
